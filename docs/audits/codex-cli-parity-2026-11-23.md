# Parity audit: Jcode и Codex CLI (Rust)

Срез на **23 ноября 2026, 03:50 AEDT** (22 ноября UTC). Сравнивались **Jcode `origin/master` [`b28c6cbdb`][j]** и **последний стабильный Codex CLI [`0.171.0`, `ccf9be8`][release]**, опубликованный 20 ноября UTC. Локальный `HEAD` Jcode был на 180 коммитов позади, но установленный бинарник сообщил нужный SHA. Установленный Codex 0.166.0 в выводах не использован: скачан отдельный бинарник 0.171.0 и проверен SHA-256 из GitHub Release API.

Цель: найти полезные отсутствующие workflows, а не посчитать одинаковые команды. **Пробел** означает, что в проверенной CLI/TUI поверхности не найден нативный контракт; **частично** означает, что задачу уже можно решить другим путём, но важная часть не покрыта. Отделены shipped от gated возможностей. В scope Rust CLI/TUI и ближайшие headless/API поверхности; не сравниваются качество моделей, Desktop, ChatGPT и управляемые облачные продукты.

## Решение

1. **P0, сначала закрыть автоматический запуск проектного MCP без решения о доверии.** Подтверждение до загрузки executable config; пользовательские серверы сохранить. Отдельно начать проектирование общей политики исполнения: tool profiles, worktree, `/plan` и текущий `/permissions` не ограничивают права процесса. Первый релиз sandbox сделать opt-in и явно отказывать на неподдерживаемых путях.
2. **P1, быстрый практический выигрыш: `jcode run` как контракт для CI.** Сначала stdin, отдельный финальный артефакт и явно одноразовый режим; затем schema конечного ответа и запуск в существующем daemon (это разные задачи). Не вводить второй headless runtime и не ломать существующий NDJSON.
3. **P1, следующий законченный workflow: ревью конкретного Git-изменения.** `--uncommitted | --base | --commit`, структурированные находки и один entry point для CLI/TUI. Оставить нынешний `/review` как «проверь работу этой сессии». Следом managed worktree для пользовательской сессии и просмотр diff, не новая Git-подсистема.
4. **P1/P2, расширяемость:** после trust gate добавить иерархию `AGENTS.md`, допуск и диагностику hooks/MCP. Не начинать с marketplace.

### P0. Доверие к источникам и разрешение конфигурации

**Codex.** Отделяет стек настроек от стека требований: defaults пакета, managed/system, cloud, пользовательский файл, профиль, проектные слои и runtime-overrides образуют обычную конфигурацию. `requirements.toml` и другие managed-источники отдельно задают ограничения. У выключенных проектных слоёв сохраняются источник и причина, но в effective config они не попадают. Без явного `Trusted` проектные config-слои выключены, включая случай `Unknown`; то же ограничивает hooks из этих слоёв и MCP, чей transport задан только там. Решение ищется по нормализованным ключам каталога/проекта/репозитория, а не по идентичности процесса daemon. [Стек и порядок][ext-c-layers], [решение trust][ext-c-trust], [фильтрация слоёв][ext-c-state], [регрессии config][ext-c-config-tests] и [MCP][ext-c-untrusted-mcp].

**Jcode.** Общий TOML грузится из `JCODE_HOME/config.toml` (по умолчанию `~/.jcode/config.toml`), затем env overrides. `load_strict` и безопасное обновление файла уже есть, но проектного TOML-стека и общего решения о доверии нет. Проект всё же влияет на prompt через инструкции/overlay и preferred tools, на skill registry и на MCP через отдельные загрузчики. В частности, MCP берёт `.jcode/mcp.json`, `.mcp.json`, `.claude/mcp.json` в каталоге сессии, сливает с пользовательскими источниками и затем раскрывает env-подстановки. Это не просто недостающий парсер: enabled MCP попадают в runtime без проверки проектного trust. [Общий загрузчик][ext-j-config], [проектный prompt][ext-j-agents], [источники MCP][ext-j-mcp-load], [регистрация MCP][ext-j-mcp-register].

**Решение.** Сначала общий `ProjectContext`: стабильный ключ каталога/repo с явно заданной семантикой linked worktree и symlink, provenance каждого источника и отдельные правила допуска для config, инструкций, skills, MCP и hooks. Не добавлять проектный TOML и hooks до проверки самого допуска; не читать решение `trusted` из repo. Для MCP применять решение до слияния, env-подстановок, запуска stdio или соединения HTTP. Сохранить доверенные пользовательские источники и объяснять, какой проектный источник выключен и почему. Не выдавать прежний допуск неявно всем существующим repo. Затем ввести типизированные слои с чёткой схемой разрешённых полей и diagnostics; constraints не должны переопределяться проектом или CLI. Типизированный порядок и слияние должны проверяться отдельным тестом: проект переопределяет разрешённое пользовательское поле, CLI переопределяет проект, но ни один из них не ослабляет независимое ограничение администратора. Полную совместимость MDM/cloud не привязывать к первому этапу.

**Приёмка.** Через реальный CLI и daemon с изолированным home открыть два проекта в одном процессе: в `unknown` и `untrusted` ни фиктивный stdio MCP, ни локальный HTTP MCP не получают initialize, глобальный сервер остаётся; в `trusted` проектный сервер появляется. Проверить коллизию имён глобального и проектного сервера, config недоверенного слоя с ошибкой, смену каталога, revoke и новый запуск/refresh, canonical aliases и два worktree. Тест должен проверять наблюдаемую регистрацию/соединение, а не только флаг загрузчика. Существующий [тест области действия MCP][ext-j-mcp-tests] полезен как основа, но доверие не проверяет.

### P1. `AGENTS.md`: иерархия и точная семантика доверия

**Codex.** Глобальный источник из Codex home поддерживает `AGENTS.override.md`. Для проекта ищет ближайший корень по `project_root_markers`, собирает от корня до `cwd`, берёт по одному файлу на каталог: `AGENTS.override.md`, иначе `AGENTS.md`, иначе настроенные fallback-имена. `project_doc_max_bytes` ограничивает проектный текст, значение `0` выключает загрузку. На этом пути проверяется **явный** `is_untrusted()`, а не отсутствие `Trusted`: unknown config-слой может быть выключен, но проектные инструкции всё ещё допущены. Менеджер сбрасывает кэш repo-источника при смене выбранных окружений или trust. [Глобальный источник][ext-c-global-doc], [проектная загрузка][ext-c-doc], [порядок и имена][ext-c-doc-path], [инвалидация][ext-c-doc-manager], [runtime-регрессия trust][ext-c-doc-trust-test].

**Jcode.** Читает `AGENTS.md` только в переданном рабочем каталоге плюс `~/AGENTS.md`, сначала проектный. Дедуп по каноническому пути уже есть. Содержимое фиксируется при bootstrap и сохраняется при восстановлении в том же каталоге, что защищает стабильность промпта. Не найдено иерархии, override/fallback, бюджета и проверки trust. [Loader][ext-j-agents], [bootstrap][ext-j-agent-bootstrap], [тесты восстановления][ext-j-prompt-tests].

**Решение и приёмка.** Добавить единый резолвер инструкций поверх P0, с перечислением источников, лимитом и отдельной политикой инструкций. Сохранить `~/AGENTS.md` как собственный глобальный контракт, не менять незаметно его порядок в существующих сессиях. Сохранять снимок при обычном reload, но при смене `cwd` или отзыве trust больше не использовать отозванный проектный текст в последующих запросах. Golden/integration: внешний parent не попадает в запрос; root + промежуточный каталог + `cwd` идут в заданном порядке; override заслоняет обычный файл; fallback и граница UTF-8 под бюджетом; untrusted сохраняет только global; pinned/restored prompt при неизменной политике не меняется. У Codex есть [тесты бюджета][ext-c-doc-budget-test] и [порядка/override][ext-c-doc-order-test].

### P1. Hooks: сохранить рабочий контракт Jcode, добавить семантику событий

**Codex.** Hook registry читает `hooks.json` и TOML из допущенных слоёв, managed requirements и вклады плагинов. Есть event-specific matchers и typed JSON input/output. `UserPromptSubmit` и `Stop` могут менять ход turn, `PermissionRequest`, `PreCompact`, `PostCompact`, `Interrupt` и другие имеют отдельные границы. `PreToolUse`/`PostToolUse` отличаются от пассивного наблюдения: могут менять то, что увидит runtime/модель. Список показывает выключенные и недоверенные записи, запуск проверяет enabled и trust декларации. Для plugin hooks проверяется также fingerprint содержимого; установка пакета не равна доверию к хуку. Есть отдельный MCP handler, а не только запуск команд. [Discovery][ext-c-hook-discovery], [допуск][ext-c-hook-admit], [fingerprint][ext-c-hook-fingerprint], [события][ext-c-hook-events], [структурированные ответы][ext-c-hook-output], [MCP dispatcher][ext-c-hook-runner].

**Jcode.** Уже есть `turn_start/end`, `session_start/end`, `pre_tool`, `post_tool`, `post_tool_feedback` и `pre_tool_transform`. Глобальные команды из `[hooks]` получают собственный контракт `JCODE_HOOK_*`; `pre_tool` умеет блокировать/переписывать вход и частично понимает Codex/Claude JSON-вердикты. Это не совместимость всего протокола: `turn_start` не `UserPromptSubmit` с verdict, `turn_end` не `Stop` с продолжением, `post_tool_feedback` добавляет обратную связь, но не эквивалентен `PostToolUse` с блокировкой результата. Нет декларативных matchers, аналогичных источников, typed событий выше или per-hook review. [Разрешение команд][ext-j-hooks], [runtime tool gate][ext-j-hook-tool], [нативные регрессии][ext-j-hook-tests].

**Решение и приёмка.** Сохранить `[hooks]` как адаптер, выделить реестр `source → event + matcher → typed outcome`. Первыми закрыть `UserPromptSubmit` и `Stop`, затем отдельно compact/interrupt/post-tool semantics. Добавлять проектные/plugin handlers только после P0 и reviewer state с fingerprint; не обещать импорт всех событий или полей сразу. Acceptance с фиктивным provider: не совпавший matcher и недоверенная/изменённая декларация не вызывают маркер; блокирующий submit не начинает запрос; `Stop` продолжает текущий turn только когда должен; post-tool verdict меняет наблюдаемый результат; старые gate, transform и feedback по-прежнему работают. Эталонные тесты Codex: [submit и Stop][ext-c-hook-turn-test], [post-tool результат][ext-c-hook-post-test].

### P1. MCP: улучшить policy и функциональность, не заменять транспорт

**Уже есть в Jcode.** Stdio, Streamable HTTP/SSE, OAuth, серверные enabled/disabled и таймауты, shared pool, `mcp`/`mcp_search`/`mcp_call`, общий session tool allow-list. Импорт поддерживаемых `[mcp_servers.*]` из `~/.codex/config.toml` одноразовый, не читает нативные проектные слои Codex и не переносит его runtime policy. [Схема и транспорт][ext-j-mcp-schema], [OAuth][ext-j-mcp-oauth], [tool allow-list][ext-j-mcp-allow], [миграция][ext-j-mcp-import].

**Частично.** Codex задаёт `required`/startup readiness, отдельные startup/tool timeout, `enabled_tools`/`disabled_tools`, per-tool policy и managed requirements для серверов; фильтрация применяется к реальному каталогу. Отдельные handlers дают `list_mcp_resources`, `read_mcp_resource`, `list_mcp_resource_templates`. Jcode предоставляет tool discovery/call, а session allow-list не выражает политику конкретного сервера и не заменяет требование готовности. Упоминание `resources/read` в transport helper не доказывает наличие model-facing resource handler. [Поля Codex][ext-c-mcp-schema], [managed checks][ext-c-mcp-requirements], [фильтрация][ext-c-mcp-filter], [required startup][ext-c-mcp-required], [ресурсы][ext-c-mcp-resource].

**Решение и приёмка.** После P0 добавить независимые `required`, `startup_timeout`, per-server allow/deny и ресурсы. Сначала пропустить policy через все потребители, включая кэш, поиск, alias/direct, `mcp_call` и reload. Один fixture из двух tool definitions проверяет, что запрещённый tool не рекламируется и не вызывается ни одним путём, в том числе после refresh каталога. Fixture с медленным сервером различает отказ запуска обязательного и деградацию необязательного. Для ресурса проверять настоящий `resources/list`, `resources/templates/list`, `resources/read` через модельную поверхность с двумя серверами и attribution, а не только JSON-RPC helper. У Codex есть [loopback-тест ресурсов][ext-c-mcp-resource-test].

### P2. Skills и локальные пакеты

**Skills частично.** Jcode уже разрешает пользовательские `~/.jcode/skills`, `~/.agents/skills`, импортирует `~/.codex/skills`, накладывает текущие `.claude/skills` → `.agents/skills` → `.jcode/skills` поверх global. Есть вызов `/<имя навыка>`, `skill_manage`, обновление, frontmatter `disable-model-invocation`; это нативная поддержка, не пробел. Codex дополнительно собирает repo `.agents/skills` по цепочке, `.codex/skills` из проектных слоёв, system/admin/user/plugin roots, получает policy/метаданные/зависимости из `agents/openai.yaml` и умеет запрашивать установку MCP-зависимости. Важно: **Codex skills не наследуют запрет disabled project config**. Они берут roots через `all_layers_high_to_low`; тест явно ждёт корень навыков из выключенного untrusted слоя. Доступность файлового окружения и skill policy при этом остаются отдельными условиями. [Jcode overlay][ext-j-skills], [импорт Codex skills][ext-j-skill-import], [frontmatter][ext-j-skill-frontmatter], [инструмент][ext-j-skill-tool]; [Codex roots][ext-c-skill-roots], [тест отключённого слоя][ext-c-skill-trust-test], [metadata][ext-c-skill-metadata], [правила отключения][ext-c-skill-config], [MCP dependencies][ext-c-skill-mcp].

**Пакеты нативно отсутствуют.** Jcode сканирует только `skills/` из установок Claude Code (manifest установок, legacy repo/cache), не весь marketplace. Этот импорт не регистрирует MCP/hooks и не создаёт install/enable/disable/uninstall lifecycle Jcode. Codex читает собственный `.codex-plugin/plugin.json` и формат Agent Plugins `plugin.json`, ведёт локальную установку/удаление и активирует связанные skills, MCP, hooks и при наличии поддержки Apps. [Импорт Jcode][ext-j-plugin-skill], [Codex manifest][ext-c-plugin-manifest], [формат Agent Plugins][ext-c-agent-plugin], [loader][ext-c-plugin-loader], [эффективные вклады][ext-c-plugin-effect], [install][ext-c-plugin-install], [uninstall][ext-c-plugin-uninstall].

**Решение и приёмка.** Сначала локальный пакет с версией, происхождением, явной активацией и атомарным изменением состояния. Начать со skills + MCP, hooks только после проверки источника и fingerprint. Для skills отдельно решить, допускаются ли repo skills в unknown/untrusted: не маркировать более строгий режим Jcode как точное копирование Codex. Если добавлять `agents/openai.yaml`, сначала policy и диагностику зависимостей, затем только подтверждаемую установку. Тест: два пакета с одноимёнными навыками и MCP, стабильная квалифицированная идентичность; disable/reload удаляет их из реально отправленного skill/tool каталога без воздействия на другую сессию; изменённый hook остаётся неактивен до ревью. Сохранить [изоляцию и приоритет навыков Jcode][ext-j-skill-tests]. Эталон [Codex per-thread disable][ext-c-plugin-disable-test] проверяет skills и tools вместе.

## Порядок реализации и критерии приёмки

- **Ограниченное исполнение.** Начать с `read-only` и `workspace-write` на одной поддерживаемой платформе и проверяемого контракта, затем второй backend. Сначала минимальный policy adapter на путях, которыми уже владеем: Bash foreground/background, `read/write/edit/apply_patch`, рабочая директория, shell env и сеть. Если MCP, hook, SDK callback, `batch`, `codemode`, spawn или workspace proxy не могут наследовать политику, ограниченный режим их блокирует либо явно требует отдельного доверия; не разрешать неявно. Тесты через настоящий daemon и `run`: чтение/запись разрешённых путей, отказ вне корня и при symlink escape, отказ network/секретному env, проверка дочернего процесса, resume и remote. Проверять эффекты, а не только текст ошибки. Нет доказательства для платформы/пути, нет обещания об изоляции на нём.
- **CI.** Сохранить смысл текущего `--json` и NDJSON. Дать однозначный stdout/stderr/exit status; stdin без промежуточного shell escaping; `-o` только для успешного финального ответа; отдельный schema контракт с capability по provider route и явной ошибкой при неподдерживаемой схеме/маршруте. `--ephemeral` описывает session persistence, не обещает отсутствие всех локальных логов, кэша или файлов команды. Acceptance: provider fixture от raw CLI до результата; валидный/невалидный schema output; отмена и ошибочный exit; отсутствие saved session с `--ephemeral`, включая штатный `resume`/picker; golden-тест прежнего NDJSON.
- **Git review.** Зафиксировать Git-цель/рабочую директорию при старте, дать одно typed событие `findings[]` с path/range/severity/message. Проверить fixture со staged/unstaged/untracked, base/merge-base и commit; после проверки рабочее дерево не изменилось. Различать «находки», «чисто» и «ревью не смогло завершиться». CI-порог по severity отдельно от транспортной ошибки. TUI и headless должны пользоваться одним путём, а не двумя похожими промптами.
- **Worktree и diff.** Доказать, что новый/forked run пишет только туда, куда его направили (это проверка cwd, не изоляции), а resume сохраняет путь. Проверить коллизию имён, грязный worktree, отсутствующий worktree, untracked/binary diff и ручные изменения. Очистка отдельным действием.

**Не брать ради паритета:** hosted Apps/Connectors, удалённый control plane с парингом и Codex Cloud `apply TASK_ID` требуют другого backend и не являются пробелом локального harness; Jcode уже имеет SSH, handoff и свою cloud поверхность. Не заменять провайдерный роутинг, swarm, `ask`, side questions или codemode клонами названий. Не обещать drop-in совместимость с форматом Codex CLI.

- Проверены `--version`, `--help`, `exec --help`, `review --help`, `sandbox --help` у официального Codex 0.171.0 и CLI/help (`run`, `session`, `mcp`, `api-bridge`) установленного Jcode на указанном SHA. Имена флагов и заявления об отсутствии проверялись также в Rust entry points, dispatch и схемах.
