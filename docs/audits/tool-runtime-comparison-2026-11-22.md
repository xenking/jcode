## Решения по приоритету

### 1. Брать сейчас: точный ответ `read` без нового режима

**Воспроизведение.** На одном и том же файле `omp-lite/src/modules/rqw-base-tools/rqw-base-tools.yml` вызов `read(start_line=30, limit=1)` показал `backend: none`. Вызов `read(start_line=1000, limit=2)` ответил `(empty file)`. Это разные состояния: пустой файл и диапазон за EOF. В jcode причина видна в `tool/read.rs:206-240,272-289`: выходная строка пуста в обоих случаях. Этот дефект не требует предположений о поведении модели.

Брать из omp-lite смысл отметки полного чтения, а не её синтаксис (`index.js:489-510`). Пусть `read` различает пустой файл, диапазон за EOF, полную выдачу и частичную выдачу с указанием продолжения. При усечённой длинной строке или отброшенной части ответа **нельзя обещать полноту**, даже если дошли до последней строки. Проверять также хвост без `\n`, CRLF, `start_line > 1` до EOF, пустую строку и ограничение внешним `batch`. Писать короткий текст по имеющимся данным; отдельный публичный тип здесь не обязателен.

**Независимая возможность ускорения.** Даже при `limit=1` обычный текстовый путь jcode вызывает `read_to_string` и проходит весь файл ради точного остатка. Лимит вывода не ограничивает память ввода. Для больших файлов испытать буферизованное чтение с ограничением размера одной строки и lookahead; если общий размер в строках неизвестен, показывать `следующая строка N`, а не выдумывать остаток. Не переносить чужой код подсчёта вслепую: omp-lite сам может сканировать байты для подсчёта (`index.js:73-79,95-128`). Отдельно проверить прежний контракт ошибок UTF-8, включая невалидные данные за окном. Сначала исправить ответ, затем измерять I/O.

### 2. Проверить в jcode: параллельные чтения без просьбы модели вызвать `batch`

В потоке jcode есть цикл по отдельным provider tool calls с проверками прерывания и фиксацией результатов (`agent/turn_streaming_mpsc.rs:1544-1619,1668-1695`; второй цикл: `agent/turn_loops.rs:1106`). Уже есть явный параллельный `batch`. Новое здесь не `join_all`, а способность **не требовать от модели правильной упаковки**. У Pi полезна механика: соседние совместимые вызовы идут одной ограниченной группой, запись или неизвестный эффект становится барьером, порядок выдачи не меняется (`src/tools.rs:72-85,121-135,201-210`; `src/agent.rs:6415-6454,6490-6527`). У omp-lite ожидание предшествующего bash перед диапазонным read показывает цену неверного порядка (`index.js:580-584,607-619`).

Предлагаемая форма: закрытый enum `ExecutionClass { ParallelRead, Barrier }` и метод **существующего** `Tool` с default `Barrier`. На первом этапе разрешать только однозначно локальные дешёвые чтения без интерактивности. Классифицировать после разрешения alias/SDK override, не по имени, не превращать классификацию в выдачу полномочий. Не переносить оптимистичное отношение к сетевым вызовам. Shell, MCP, SDK, пользовательские инструменты, wrappers и непонятные аргументы остаются барьерами. Политика и лимиты не должны зависеть от того, кто вызвал инструмент. Отдельно решить, менять ли обещанную семантику явного `batch` и `Promise.all` в `codemode`; не менять их молча в первом эксперименте.

Критические проверки: два чтения реально перекрываются; `read A → edit A → read A` возвращает старое и новое содержимое соответственно; порядок tool IDs в истории сохраняется при обратном порядке завершения; отмена и rebuild не дублируют и не теряют результаты; denied/custom tool не исполняется в обход registry. Проверить оба turn loop. Это оптимизация по умолчанию **только после** доказанного выигрыша на естественных native multi-call, а не новый пользовательский режим.

### 3. Эксперимент, не default: якорь из `read/agentgrep` прямо в `edit`

У omp-lite интересен не hash сам по себе. Только полностью **показанная** и проверенная строка становится доступным якорем: выдача поиска может быть достаточной для правки без повторного `read`. Усечённая строка, устаревший снимок и неподходящий файл не получают обещания редактируемости (`index.js:95-128,231-250,464-510`). В Pi есть отдельная пара `read(hashline=true)` / `hashline_edit` (`src/tools.rs:6362,7992-7995,13028-13042,13243+`). Jcode сейчас применяет список точных `old_string/new_string` под файловой блокировкой, сначала валидирует весь список, потом пишет (`tool/edit.rs:79-153,191-205,634-671`). Это хороший baseline: короткая уникальная замена часто проще якоря.

Испытать опцию **формата файловых инструментов сессии**, не второй `ToolRegistry`. Контракт: идентичность файла + версия + диапазон полностью показанных строк. Сверить под блокировкой непосредственно перед записью. При изменении вернуть небольшой свежий фрагмент и не писать; не использовать короткий хеш как право на запись. В `codemode`/`batch` строка, отброшенная агрегатором, не считается показанной модели. Для первого прототипа разумнее вовсе не выдавать якоря по этим маршрутам. Остальные инструменты, включая `apply_patch`, остаются без изменений. Не тащить в default частичный многофайловый успех omp-lite: ошибка может означать, что часть файлов уже записана (`index.js:373-461,615-643`).

### Что оставить как есть

- **Не копировать `xdev` целиком.** Сначала проверить реальную дыру: частые ли встроенные инструменты раздувают eager-схемы у провайдера без native deferred loading? В jcode `load_tools` при отсутствии поддержки не откладывает builtins, а для MCP есть отдельный search/call. Если накладные расходы существенны, испытывать компактный профиль только на этой поверхности. Не заменять stable prefix новой схемой каждый ход и не путать «не показывать» с «запретить».
- **Не заводить второй spill для всех инструментов только потому, что он есть в Pi.** Осмысленный кандидат уже: `batch` режет текст в доле от 50 000 байт и ставит `(truncated)` (`tool/batch.rs:318-343`); `codemode` умеет давать путь к полному отчёту. Проверить, как часто после обрезки повторяется дорогой вызов. Если часто, дать переиспользуемую ссылку на полный результат с изоляцией по сессии, лимитом места и сроком хранения. Не писать секреты в новый постоянный лог. Pi показывает образец разделения preview и артефакта (`src/tools.rs:1882-1964,8756,10424,14891`).
- **Не копировать provider-specific rewrite и внутренние импорты OMP.** Для расширения, которым ядро не владеет, эталон схем и предупреждение о дрейфе разумны. Jcode владеет и определениями, и сериализацией: полезнее проверять конечный provider payload, включая разрешения, совместимость alias и закэшированный префикс. Не переносить private endpoint веб-планировщика или текстовый фильтр `eval` как границу безопасности. В omp-lite нет обнаруженного файла LICENSE в проверенном дереве: предлагаются собственные реализации поведения, не перенос исходников.

## Как решить, что действительно быстрее

Ни одно сравнение wall time, RSS, токенов или успешности задач между продуктами здесь не выполнялось. Запуск unit-тестов OMP этого не заменяет. Ниже план эксперимента, не результаты.

1. **I/O без LLM.** Идентичные UTF-8 fixtures 1, 32, 128 МиБ, включая одну гигантскую строку. Первый экран, окно в середине и конец. По 10 парных вызовов на сценарий, менять порядок A/B, отдельно учитывать прогретый кэш. Проверять байты чтения, пик RSS и время, идентичность видимого диапазона и достоверность подсказки. Рост RSS на величину полного файла при запросе первого экрана означает, что задачу не решили.
2. **Исполнение без LLM.** Один записанный provider response, содержащий 1, 2, 4 чтения либо чтения с записью между ними. Сравнить обычный вызов, существующий `batch` и новый scheduler. По 30 парных повторов; отдельно время до первого результата и до последнего, p50/p95, порядок, отмена. Прогон со шлагбаумом в тестовом инструменте доказывает перекрытие, замер реального I/O отдельно показывает его ценность. Не объявлять всю сессию быстрее из-за искусственного sleep.
3. **Польза для модели.** Одинаковые модель, provider, бюджет, задания и начальные деревья. По 5 парных прогонов на задание: уникальная правка, повторяющиеся строки, большой блок, устаревшая выдача, независимые файлы. Сравнить exact edit, существующий patch и якоря. Считать правильный конечный diff, повторные `read`, tool rounds, input/output/cache tokens и wall time до принятой правки. Не принимать снижение токенов ценой лишних неверных правок. Разделить холодную и тёплую сессии, хранить только синтетические данные в изолированном `JCODE_HOME`.

**Решение о форме.** Исправление `read` относится ко всем. Расписание вызовов принадлежит агентному циклу и требует только узкого контракта эффекта. Формат якорей меняет то, как модель читает и редактирует, поэтому имеет смысл как экспериментальный профиль. Принцип *Minimize Reader Load* здесь меняет конкретный выбор: один путь разрешений и выполнения вместо параллельной иерархии «обычных» и «лёгких» инструментов.
