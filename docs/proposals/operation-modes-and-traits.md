Статус: предложение, 21 ноября 2026 UTC. Этот RFC не меняет runtime, конфиг или формат сессий. Срез Jcode: `c9cce147d98d7d50a9c9631f33baf12a0ff69261`. Срез Desktop: `84fd788b2d1de4835ac9994717929c6b71247f16`. Ниже «сейчас» означает чтение исходников этих ревизий, а не проверку установленного Desktop. **Что дублируется в меню.** В Desktop одна запись `SKILL.md` доступна через два входа: `/имя` в общем slash-поиске и `/mode имя` в picker. Внутри picker активный skill показывается только в **Active**. Остальные разбиты на **Modes** (`mode: true`, иначе `selfdev`, `swarm` и имена `*-mode`) и **Skills**; `mode: false` отключает эвристику, не запрещает pin. **Actions → off** есть только при pins. Это повтор навигации, не две строки одного picker. Desktop общий slash-поиск фильтрует одинаковые `value`; TUI объединяет built-ins, локальные и remote skills через `seen`. Коллизия имени с built-in реальна: например, TUI `/swarm` и `/selfdev` не превращаются в две строки. Desktop parser имеет исключение для skill `selfdev`, но защищает другие имена встроенных команд. [Desktop groups][d-picker], [classification][d-catalog], [slash merge][d-slash], [dispatch][d-skill], [TUI merge][tui-picker].

**Что дублируется в контексте.** Обычный pin пишет тело skill в скрытый transcript reminder `# Active Skill`, а в системном каталоге присутствуют только имя и описание. Это два представления, но не двойная инъекция тела. Daemon и локальный TUI не передают pinned body в конструктор system prompt. Desktop на этом маршруте передаёт имя, не тело. SSH TUI активирует pin отдельной командой, а последующий ход не передаёт ни skill name, ни skill reminder. [SSH dispatch][tui-skill-ssh], [wire][tui-skill-wire]. Тесты daemon проверяют один reminder для неизменного pin при повторном attach, restore и после compaction, в том числе у наследника. Два настоящих пути повторения текста остаются: смена списка `[A]` на `[A, B]` создаёт новый **полный** roster, пока старый виден в истории, а явный `skill_manage load` возвращает тело в tool result независимо от pin. Для `selfdev` отдельно существует встроенная self-dev инструкция с похожей задачей, а также возможен внешний skill; имя не доказывает совпадение текстов. Не считать чтение `SKILL.md` моделью, metadata меню, provider cache replay и новую инъекцию одним событием. [System prompt][j-static], [TUI prompt][tui-static], [roster][j-storage], [restore/compact tests][j-pin-tests], [load][j-skill-tool].

## Предложение

У сессии **ровно один** `OperationMode = Agent | Ask | Plan` и **0..n** `TraitRef` в упорядоченном множестве. `TraitRef` ссылается на тот же skill в каталоге (`scope`, `id`, `revision`), а не на копию `SKILL.md`. Skill можно вызвать на один ход или закрепить. Trait добавляет инструкции, не выдаёт разрешений, не меняет модель, не запускает worker. `model/effort`, approval posture и self-dev/ambient остаются независимыми. Встроенные workflow продолжают использовать тот же слой команд; новый «режим для каждого workflow» не нужен.

Daemon выводит `mode`, `plan_state`, `traits` и effective capabilities одной проекцией для TUI, Desktop и SDK. Один общий парсер runtime-команд и один workflow для Plan заменяют два prompt-шаблона. Один набор вариантов для списка skills и traits; способы «вызвать один раз» и «закрепить» выбираются на той же строке. Дедуп по разрешённому ID, а не по похожим текстам. При коллизии built-in сохраняет shortcut; skill остаётся доступен через явное действие `Run skill`. Смена traits не запускает model turn.

### Граница исполнения и approval

1. **Ask** разрешает чтение из допустимых источников и ответ. **Plan** разрешает то же, `ask` для уточнений и `submit_plan` в типизированное хранилище сессии. Ни один режим не разрешает писать в checkout, менять Git, запускать произвольный процесс, изменять память/конфиг или внешнее состояние. Записи daemon в собственный журнал и plan store допустимы, но не дают модели произвольного пути. Экспорт плана в рабочее дерево отдельно инициирует человек.
2. Владелец проверки один: серверный admission/dispatch и тот же policy engine в standalone local TUI. Чтение из файлов проверяет разрешённые ресурсы. Из `session policy ∩ operation mode ∩ inherited scope` получается верхняя граница; deny побеждает allow. Учитывать каноническое имя, аргументы после hooks и реальные эффекты. Неизвестный эффект запрещён в Ask/Plan. Скрытие tools в prompt необязательно и не считается enforcement. Публичные API, ACP, очереди/retry/resume и direct tool calls проходят ту же проверку. MCP без доверенной гарантии read-only, shell, произвольные hooks, GUI, plugin load, scheduler и вложенные вызовы нельзя пропускать по одному имени `read`. Начать с явного набора локальных read-only leaf tools. [Текущий dispatch][j-dispatch], [codemode dispatch][j-codemode].
3. В пилоте Ask/Plan не запускают workers и wrappers общего назначения. Позже вложенные вызовы в `codemode`/`batch`, MCP, async tasks и child workers получают неизменяемый parent ceiling и собственное сужение. Проверять каждую leaf operation и dispatch дочернего хода. `Wake` уже существующего агента, переподключение и смена модели не обходят ceiling. При смене режима активные writes завершаются/cancel до ACK либо сервер отвечает Busy. Нельзя обещать, что уже запущенные эффекты отменились.
4. `Plan(Draft) → Plan(Review{id, revision, digest})`. Правка создаёт новую версию, Reject возвращает Draft, ничего не запускает. **Approve & Build** от авторизованного человека атомарно сохраняет решение, назначенного исполнителя и durable queue item Agent. Очередь принимает его по идентификатору approval, не обещая exactly-once для внешних эффектов. Сервер сверяет session/workspace identity и базу плана, digest, policy epoch, actor и срок. Stale, timeout, decline, auto-recommendation `ask`, модель или чужой worker не могут подтвердить. Повтор того же ID отдаёт receipt без второго запуска. Reconnect/reload восстанавливает pending или уже поставленный turn, а не повышает rights повторно. Явный уход из Plan возможен без Build, с отменой pending; текст «да» сам ничего не делает. Approval плана разрешает начать реализацию в scope, не заменяет отдельные разрешения на tool, внешний эффект или платный spawn.

### История, совместимость и cache

- Сохранять session ID, сообщения, tool results, выбранные model/effort, файлы плана и provenance. `pinned_skills` читать первым, fallback на singleton `pinned_skill`. Трактовать legacy pins как traits в `Agent`, не как новое разрешение, и не переписывать старый transcript. Если skill исчез, показать provenance/статус, не молча подменить одноимённым из другого scope. Прочитанная копия исторического prompt не является действующим разрешением. Для будущих клиентов согласовать capability; старый клиент может читать сессию, но не обходить restricted mode legacy полем `active_skill`.
- Сохранить `/mode <skill>`, `/mode toggle <skill>`, `/mode off` и текущие `/skill [текст]` с pin. `off` снимает только traits. Для one-shot добавить явное действие `Run once`, не менять поведение shortcut. `/plan [цель]` начинает тот же сценарий планирования, но теперь daemon ждёт структурированное решение; новый `/ask [вопрос]` переключает операционный режим. При коллизии существующего `ask`/`plan` skill оставить явную адресацию. Desktop Draft modes и shortcuts click/Tab/Enter/Esc остаются, TUI не переназначает существующие клавиши под Cursor. TOML/настройки инструментов, `[agents]` и keymaps не требуют миграции.
- Отдельно хранить state и историю. Сохранить замороженный system prefix и штатный replay. На смену append компактный state event; первый ввод новой ревизии trait добавляет тело один раз. Полная активная проекция восстанавливается после compaction, не добавляется на каждом turn и не изменяет старые provider messages. Различать живой transcript с историческими телами и заново собранную проекцию, в которой активная ревизия должна быть одна. Если capability меняет tool schemas, безопасная поверхность важнее hit: не переиспользовать stale разрешения, а cache сравнивать только между совпадающими route/account/prefix/tool schema. Не делать prewarm, resize, premium wake или rebuild контекста при открытии picker. [Замороженный prompt][j-static], [replay проверка][j-pin-tests], [существующий cold gate][j-cold].

### Кто строит и кто отвечает

**Сценарий.** Пользователь выбирает сильную модель для Plan, например Astra, с явно разрешённым route. Модель исследует и сдаёт `plan@v1`. Пользователь правит Markdown до `v2` и нажимает **Approve & Build with Sol** (или Terra). Сервер передаёт точный утверждённый digest, текст и ограниченный набор refs. Sol/Terra становится владельцем исполнения, работает сам или запускает разрешённых workers. Итог приходит пользователю напрямую от Sol/Terra, без recap, judge, final rewrite или автоматического пробуждения Astra. Дополнительная консультация остаётся отдельным, явным, бюджетированным вызовом по [supervisor-consult](../research/supervisor-consult.md#как-отвечать-и-где-решать).

| Вариант | Контекст, адрес и права |
| --- | --- |
| **Смена модели в той же сессии. Рекомендуемый пилот.** | Сохраняет один чат, историю и plan receipt. Между ходами меняет подтверждённый `model/effort` и admission policy, не запускает перевод/пересказ дорогой моделью. Новый provider/account может получить холодный prefix и иную поддержку reasoning/tool replay. Не форсировать дорогую compaction. |
| **Handoff в адресуемую сессию. Следующий эксперимент.** | Явно целится в `session_id` или `host/rig/seat`; передаёт `source_session`, `plan_id@revision`, digest, repo/worktree/base, границы задачи, необходимые refs и выбранный route. Не копирует transcript, секреты или bearer approval. Source/target связаны в UI; пользователь продолжает в Target, не получает пересказ Source. Target валидирует собственную authority по receipt и principal, scope не расширяется. Подготовка inbox не означает admit/wake. При холодном либо неизвестном target стоимость проверяется до dispatch, никакого implicit wake. Обе сессии остаются читаемыми. |

Активация существующего seat, provider cache и наличие budget не одно и то же. Существующие model allowlist и effort caps только ограничивают допустимые worker routes. Premium spawn/wake требует отдельного подтверждения или явного пользовательского бюджета с route, целью, потолком и сроком. Проверять допуск при dispatch и после retries/failover; неизвестная цена или отсутствие человека не превращаются в согласие. Пилот не добавляет классификатор, автоматический premium fallback или постоянно активного консультанта. [Политика spawn][j-spawn], [cold wake][j-cold].

### Эскиз и acceptance

```text
[Plan ▾] [Traits: selfdev · swarm +] [Planner: Astra / high]
  Operation: ( ) Agent  ( ) Ask  (●) Plan
  Traits:    [x] selfdev [x] swarm [ ] poteto-mode
  /skill:    Enter legacy  |  Run once  |  Pin or unpin

Plan v2 · Waiting for approval · edits blocked
[Edit] [Keep planning] [Approve & Build: Sol / high]
After ACK: [Agent ▾] [Model: Sol / high]  Plan v2 approved ✓
```

| Проверка будущего пилота | Условие принятия |
| --- | --- |
| Паритет Desktop, local TUI, remote TUI и SDK | Один каталог/ID, одна строка на trait, без расхождения с ACK. Legacy сессия с одним и несколькими pins сохраняет порядок, историю и shortcuts после reconnect. Узкий TUI не переносит chrome, сокращает trait chips. |
| Fake provider через настоящий daemon | В Ask/Plan direct, nested и queued/replayed write, shell, MCP, GUI и spawn не дают побочных эффектов. Проверить stale worker, legacy SDK, batch и alias после rewrite. Read и Plan `submit_plan` работают. В Agent те же контролируемые fixtures исполняются только в разрешённом scope. |
| План и ответ | Два клиента видят v1/v2. Reject, stale approval, headless auto-answer, чужой actor и replay не запускают build. Двойное нажатие и daemon restart дают один build для v2. Sol/Terra получает v2, а после approval счётчик обязательных запросов к planner равен нулю. Worker не выдаёт approval и не отвечает вместо владельца. |
| Cache и экономика | Захватить запросы fake provider до/после pin, resume и compact: неизменные системные bytes при pin-only, ни одной новой копии на обычном turn, понятное отличие schema/route change. Затем парный пилот на сопоставимых задачах против single-model Plan→Build. Считать принятый outcome, rework, время до плана и до проверенного результата (p50/p95), все запросы включая retries, fallback и фон, uncached/cache read/cache write/reasoning/output, реальные debits и денежную стоимость отдельно. Если quota units не наблюдаемы, так и указать. Stop при bypass, потере истории, скрытом premium запросе или существенном ухудшении качества. Экономия не заявляется без наблюдений. |
