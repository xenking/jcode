# Реестр изменений форков Jcode

Снимок на 20 ноября 2026 года. `jcode` означает `xenking/jcode:master`, `jcode-desktop` означает `xenking/jcode-desktop:main`. В каждой строке перечислены опорные коммиты, а не вся цепочка разработки. Вспомогательные тесты, форматирование и lockfile сгруппированы с соответствующим поведением или проверками. Статус **origin** означает «есть в основной ветке форка, выкачено неизвестно». Проверки ниже предназначены для повторного прогона после синка и не являются отчётом об их прохождении.

Источники: `git log upstream/master..origin/master` и `git log upstream/main..origin/main` в соответствующих репозиториях, изменённые пути и дерево origin. Контекст сверялся через `session_search` с `working_dir` обоих проектов, файлы `~/.jcode/sessions/` (сессии `sloth`, `turkey`, `raccoon`) и две сессии стороннего агентного инструмента (CLI и Desktop; идентификаторы не публикуются). Сессии не доказывают публикацию и не заменяют Git.

### CI форка

Обычный push в `master` запускает Quality Guardrails, Linux Build & Test и TypeScript SDK. PR и ручной запуск того же `CI` дополнительно проверяют macOS, Windows, ARM64, PowerShell и установщик. Сборка release-профиля остаётся в полном CI. Отдельный tag/manual `release.yml` не меняется.

Перед `quick-release` нужен зелёный push и зелёный ручной `CI` на одном SHA. Выберите ветку, указывающую на этот коммит, и запустите `gh workflow run ci.yml --repo xenking/jcode --ref <ветка>`. Этот запуск делает проверки и не публикует релиз. Новые push/PR не отменяют его.

`scripts/check_fork_removals.py` блокирует sync, если upstream возвращает дополнительные workflows или расширяет матрицу push. `python3 scripts/test_fork_ci.py` проверяет маршрутизацию, `python3 scripts/test_quick_release.py` проверяет запрет тега без обоих прогонов. Бюджеты размера, паник и проглоченных ошибок фиксируют накопленный долг форка на `52016d2ef` с учётом форматирования. Правила не менялись и отклоняют дальнейший рост.

## Как вести реестр

1. Добавляйте/обновляйте строку вместе с фичей или фиксом. Если её первый коммит ещё не имеет устойчивого SHA, укажите SHA предшествующего коммита той же серии либо закрепите SHA фичи отдельным docs-коммитом непосредственно за ней. Коммит не может содержать собственный SHA. Для Desktop включайте обновление реестра в ту же поставку двух репозиториев.
2. В колонке «Коммиты» используйте короткие уникальные SHA в обратных кавычках через запятую. Одна строка описывает одно поведение в одном репозитории. Неподтверждённую реализацию держите только в отдельной секции. Не приравнивайте push к раскатке.
3. До публикации синка обязательно проверяйте **итоговые коммиты**, даже если merge не вызвал конфликтов. `scripts/xk-upstream-sync.sh` делает это после merge и перед push после возможного догоняющего merge с `origin`. `--skip-checks` не отключает guard. Для ручного синка запустите из парного CLI checkout, подставив конкретный ref вместо `HEAD`, если публикуете не текущий коммит:

   ```sh
   scripts/check_fork_removals.py jcode . HEAD
   scripts/check_fork_removals.py desktop ../jcode-desktop HEAD
   scripts/test_fork_removals.sh
   ```

   Фикстура использует только локальные Git remotes. Синк не должен публиковать бесконфликтное слияние, вернувшее workflow из upstream или из обновившегося `origin`. Исправленный коммит проходит проверку. Добавляйте правила только по подтверждённому решению форка, не по одному `git diff`. При сознательной смене решения обновите запись и guard.
4. После синка обновите обе локальные ссылки `origin` и проверьте предков:

   ```sh
   git fetch origin master
   git -C ../jcode-desktop fetch origin main
   python3 scripts/check_fork_ledger.py
   ```

   Если Desktop не рядом, передайте `--desktop /путь/к/jcode-desktop`. Скрипт проверяет локальные remote-tracking refs и ничего не меняет. Ошибка ancestry требует сверки с форком и upstream, а не удаления записи.
5. Прогоните проверки из колонки «Проверка» на результате синка. `--help` указывает вход в сценарий и его параметры, сам по себе он не проверяет поведение. Git ancestry не обнаружит revert или потерю поведения при разрешении конфликта. Для сценариев используйте отдельный `JCODE_HOME`, `JCODE_TEST_SESSION=1` и отдельный сокет, не трогая установленный daemon или Desktop.
